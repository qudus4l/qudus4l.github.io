FROM CONSTRAINT TO DELIVERY

The improvement had to reach the routine.

After a skin scan, a person needs a routine drawn from products the catalog can actually offer. Search determines what the generator has to work with.

  1. 01

    The bottleneck

    Comparing vectors in PHP was slow and hit memory limits. A small candidate pool kept the work manageable, but narrowed the products available to the generator.

  2. 02

    My decision

    I moved ranking into PostgreSQL with pgvector, then checked whether routine generation used the new search path. Its old candidate limit still constrained what the faster search could consider.

  3. 03

    What changed

    Search became faster and could consider more candidates. That gave routine generation a wider pool to work with; recommendation quality still needed separate evaluation.

FOUR DECISIONS / ONE SYSTEM
01 / 04

Search limits become product limits.

Search supplies the products used to generate a routine. If it considers too few, a useful option may never reach the model.

IN OYSTER

The PHP path reads stored vectors in batches, compares them, and sorts the scores. The pgvector path ranks inside the database and returns matching IDs before the application loads the selected products.

The application decides which products are eligible. The database ranks within that boundary. Faster ranking does not remove the need to choose the right candidates.
